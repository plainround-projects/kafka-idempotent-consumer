# Runbook: "the balances look wrong" or "the balance updater looks stuck"

This is the lesson's step 6: one page, one row per failure, in the order you would check them during an incident (cheapest signal first). Every signal below is something this project prints or can query today.

| # | Check | Signal you can see | Cause | Fix |
| --- | --- | --- | --- | --- |
| 1 | **Is the group keeping up?** `kafka-consumer-groups.sh --describe --group balance-updater` | `LAG` per partition grows while the process is alive; the log has `Consumer poll timeout has expired` and `EVICTED: offset commit rejected ... error=CommitFailedError`; members come and go (rebalances). | A batch takes longer than `max.poll.interval.ms`, because `max.poll.records` times the time per record is too large. The group evicts the member even though it is healthy, and the batch is redelivered. | Size the batch to fit: lower `max.poll.records` so one batch is well inside the interval (`--max-poll-records 50` in `make demo-evict`), or write each batch in one database round trip. Do not simply raise `max.poll.interval.ms`: lag keeps growing and a really stuck consumer is detected later. |
| 2 | **Is anything parked?** Count of records in `payments-dlq`; log lines `dead-lettered ... partition=p offset=o`. | `payments-dlq` grows; each record carries `originalTopic`, `originalPartition`, `originalOffset`, `error`, `raw`. Lag on `payments` is zero. | A record that can never be processed: a malformed amount, bad JSON, a missing field, an unknown account. Retrying changes nothing. | Read the `error` field, fix the producer or the data, then replay the `raw` payload to `payments` (`originalOffset` says where it came from). The consumer needs no change; it already moved on. |
| 3 | **Are the numbers right?** `make queries` and the checker (`python -m idempotent_consumer.interfaces.check_cli`, or your reconciliation against the source of record). | `MISMATCH acct-017: expected 4821.33, got 4903.81 (off by +82.48)`; the difference equals one payment's amount; `processed_events` has fewer rows than payments applied, or the log's `'duplicate'` counter is 0 after a crash. | A payment was applied twice: the consumer crashed between the database commit and the offset commit and has no guard (the naive consumer), or the guard is not in the same transaction as the balance update. | Insert `eventId` into `processed_events` in the same transaction as the balance update and skip when it already exists (`--mode idempotent`). To repair data already wrong, subtract the duplicate amounts, found by grouping the topic's events by `eventId`. |
| 4 | **Did the process die?** Exit codes and restarts; the last log line. | The log ends with no `done:` line; the process manager shows restarts; lag is flat. | A crash (out of memory, a killed container, an unhandled database error). Kafka redelivers from the last committed offset on restart. | Restart. With the idempotent consumer the redelivered events show up as `'duplicate'` and change nothing. Find the crash cause in the stack trace. |

How to read it during an incident: lag first (one command, tells you whether the consumer is consuming at all), then the dead-letter count (explains a few missing payments), then the balance check (explains numbers that are wrong rather than missing).
